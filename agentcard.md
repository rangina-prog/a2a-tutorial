## Discovery Mechanisms

Clients can find Agent Cards through three channels:

1. **Well-Known URI** — The standard approach. Fetch from:
   ```
   https://{domain}/.well-known/agent-card.json
   ```

2. **Registries / Catalogs** — Curated directories of agents (Agent marketplaces, platform catalogs).

3. **Direct Configuration** — Pre-configured Agent Card URLs or inline card content (use case is private/internal agents).

---

## Steps: Define, Serve, Consume

1. **Define** — Create the Agent Card JSON describing the agent's metadata. This can be done using the A2A SDK (`AgentCard` type), auto-generated by a framework (e.g. Strands infers it from the agent definition), or written manually as a JSON file.
2. **Serve** — Expose the card at a well-known URL (usually `/.well-known/agent-card.json`). This is handled automatically by the A2A SDK server or framework, or can be a plain HTTP route returning the JSON file.
3. **Consume** — Clients fetch the card, read skills and interfaces, and start sending messages. The client library (from the A2A SDK or framework) fetches and parses it.

The SDK and frameworks make this easier and less error-prone. The Agent Card itself is JSON over HTTP — no special tooling is strictly required to produce or consume it.

---

## There Is No "Handshake"

Unlike protocols like WebSocket or TLS, there is no formal handshake in A2A. There is no connection negotiation. The flow is:

1. Client reads the Agent Card (the closest thing to a "handshake" — the client learns what the server supports)
2. Client sends a JSON-RPC request
3. Server responds

Every request is independent. There is no persistent connection unless SSE streaming is used, which is a one-way server-to-client stream after the initial POST. The client can send one request and walk away, or send a hundred. Each one is a standalone HTTP POST with a JSON-RPC payload.

## Agent Card Structure

The Agent Card is the most important discovery object in A2A. Below is a complete breakdown of the top-level fields.

### Top-Level Fields

| Field | Type | Required | Description |
|:------|:-----|:---------|:------------|
| `name` | string | Yes | Human-readable agent name |
| `description` | string | Yes | What the agent does |
| `version` | string | Yes | Agent version (e.g., `"1.2.0"`) |
| `supportedInterfaces` | array | Yes | Protocol bindings with URLs (ordered by preference) |
| `capabilities` | object | Yes | What A2A features the agent supports |
| `defaultInputModes` | array | Yes | Accepted input MIME types |
| `defaultOutputModes` | array | Yes | Produced output MIME types |
| `skills` | array | Yes | What the agent can do |
| `provider` | object | No | Organization info |
| `securitySchemes` | map | No | Auth scheme definitions |
| `securityRequirements` | array | No | Which schemes are required |
| `documentationUrl` | string | No | Link to docs |
| `iconUrl` | string | No | Agent icon |
| `signatures` | array | No | JWS signatures for integrity |

## How Discovery Works in Practice

Assume two agents exist and have been set up correctly by their respective developers, meaning each is:

- Built with its **own framework**
- Exposing an A2A-compliant **JSON-RPC endpoint**
- Serving an Agent Card at its well-known URI

**Step 1:** Agent A needs to send a task to Agent B. It knows Agent B's domain (or has been given Agent B's URL through configuration). Before Agent A can send any work to Agent B, it needs to understand what Agent B can do, what input it accepts, what authentication it requires, and where to send requests. This is what discovery solves.

**Step 2:** Agent A sends a simple HTTP GET to Agent B's **well-known URI**. Agent B's A2A server framework responds with the Agent Card — a JSON document describing everything Agent A needs to know.

**Step 3:** Agent A's A2A client library **parses this card**, checks that it supports a compatible protocol binding (e.g. JSON-RPC), verifies it can satisfy the authentication requirements, and identifies which skills match the task at hand.

From this point, Agent A has everything it requires to communicate with Agent B.

The entire exchange happens before any actual task work begins. Discovery is the step that makes the conversation possible.

```
Agent A (Client)                              Agent B (Server)
     |                                              |
     |  GET /.well-known/agent-card.json            |
     |--------------------------------------------->|
     |                                              |
     |  200 OK                                      |
     |  {                                           |
     |    "name": "Support Agent",                  |
     |    "skills": [...],                          |
     |    "capabilities": { "streaming": true },    |
     |    "securitySchemes": { "entraId": {...} },  |
     |    "supportedInterfaces": [{                 |
     |      "url": "https://...",                   |
     |      "protocolBinding": "JSONRPC"            |
     |    }]                                        |
     |  }                                           |
     |<---------------------------------------------|
     |                                              |
     |  Agent A now knows:                          |
     |  - What Agent B can do (skills)              |
     |  - Where to send requests (url)              |
     |  - What protocol to use (JSONRPC)            |
     |  - What auth is needed (Entra ID JWT)        |
     |                                              |
     |  POST /a2a/v1  (JSON-RPC message/send)       |
     |--------------------------------------------->|
     |  ... task execution begins ...               |
```

## Skills Field

Skills represent the distinct capabilities an agent can perform. They are the primary mechanism for clients to understand what an agent is good at.

| Field | Required | Description |
|:------|:---------|:------------|
| `id` | Yes | Unique identifier |
| `name` | Yes | Human-readable name |
| `description` | Yes | Detailed description |
| `tags` | Yes | Keywords for matching |
| `examples` | No | Example prompts or scenarios |
| `inputModes` | No | Override agent-level input modes |
| `outputModes` | No | Override agent-level output modes |
| `securityRequirements` | No | Skill-specific auth requirements |

Skills are largely descriptive — they help clients decide which agent to route a request to. The `tags` and `examples` fields are useful for programmatic agent selection.

## Supported Interfaces

The `supportedInterfaces` array declares all **protocol bindings** the agent supports, ordered by preference (first entry is preferred):

```json
"supportedInterfaces": [
  {
    "url": "https://agent.example.com/a2a/v1",
    "protocolBinding": "JSONRPC",
    "protocolVersion": "1.0"
  },
  {
    "url": "https://agent.example.com/a2a/grpc",
    "protocolBinding": "GRPC",
    "protocolVersion": "1.0"
  }
]
```

Clients select the first interface they support from this list.

---

## Capabilities

The `capabilities` object declares optional features:

| Field | Type | Meaning |
|:------|:-----|:--------|
| `streaming` | boolean | Supports SSE / gRPC streaming |
| `pushNotifications` | boolean | Supports webhook-based async updates |
| `extendedAgentCard` | boolean | Offers a richer card after authentication |
| `extensions` | array | Protocol extensions supported |

If a client tries to use a capability the agent has not declared, the agent returns an appropriate error (e.g., `UnsupportedOperationError`).

## Security Schemes

The `securitySchemes` field declares what authentication methods the agent requires. This is an optional field — agents can operate without it, but it is useful for enterprise deployments as it communicates to clients what credentials are needed before any request is sent.

A2A aligns with [OpenAPI Security Scheme](https://swagger.io/specification/#security-scheme-object) patterns. The `securitySchemes` map defines named schemes, and the `security` array specifies which schemes (and scopes) are required.

### Supported Scheme Types

| Scheme Type | Field | Use Case |
|:------------|:------|:---------|
| **OpenID Connect** | `openIdConnectSecurityScheme` | Enterprise IdPs like Entra ID, Auth0, Okta — client discovers endpoints via the OIDC discovery URL |
| **OAuth2** | `oauth2SecurityScheme` | Standard OAuth2 flows (client credentials, authorization code) |
| **HTTP** | `httpSecurityScheme` | Bearer tokens, Basic auth, or custom HTTP auth headers |
| **API Key** | `apiKeySecurityScheme` | Static API keys passed in headers or query parameters |

### Example: OpenID Connect with Entra ID

```json
"securitySchemes": {
  "entraId": {
    "openIdConnectSecurityScheme": {
      "openIdConnectUrl": "https://login.microsoftonline.com/{tenant-id}/.well-known/openid-configuration"
    }
  }
},
"security": [{ "entraId": ["api://{app-client-id}/.default"] }]
```

The `security` array references the named scheme and lists the required scopes. A client reading this card knows it needs to obtain a JWT from the specified Entra ID tenant with the given scope before making any request.

### Example: API Key

```json
"securitySchemes": {
  "apiKey": {
    "apiKeySecurityScheme": {
      "in": "header",
      "name": "X-API-Key"
    }
  }
},
"security": [{ "apiKey": [] }]
```

### How Clients Use Security Schemes

1. Client fetches the Agent Card
2. Reads `securitySchemes` to understand what auth is needed
3. Reads `security` to know which scheme(s) and scope(s) are required
4. Acquires the appropriate credentials (token from IdP, API key from config, etc.)
5. Includes the credentials in subsequent requests to the agent

Security schemes are declarative — they tell clients what is needed, but the agent's infrastructure (platform, gateway, runtime) is responsible for actually enforcing the auth. The Agent Card is the discovery mechanism, not the enforcement mechanism.

### Skill-Level Security

Individual skills can declare their own `securityRequirements`, overriding the agent-level `security` field. This allows agents to expose some skills publicly while restricting others to authenticated clients — a pattern that pairs well with the Extended Agent Card feature.

## Caching

Agent Cards change infrequently. The spec recommends standard HTTP caching:

**Server side:**

- Include `Cache-Control` with appropriate `max-age`
- Include `ETag` derived from the card's version or content hash
- Optionally include `Last-Modified`

**Client side:**

- Honor HTTP caching semantics (RFC 9111)
- Use conditional requests (`If-None-Match`, `If-Modified-Since`) when cache expires
- Apply a default cache duration if the server does not provide caching headers
